# Gravity Golf

A puzzle golf game on tiny solar systems, built in **Unreal Engine 5.9** (preview) by Claude Code alone.
`docs/VISION.md` is the design and business plan. `legacy/` holds the 2022 web version for reference (gitignored).

## Principles

- **Code-first.** Everything that can be text is text. Gameplay is C++, holes are JSON, materials are generated by
  Python. Never hand-edit a `.uasset` you could regenerate; change the script and re-run it.
- **Deterministic simulation.** `Source/GravityGolf/*/Sim/GGSim.*` is plain C++ (no Unreal types). It uses only
  `+ − × ÷ √` on doubles, with FP contraction off, so shots replay bit-identically everywhere. Derived trig values
  are quantized in the loader. Keep it that way: no `sin`/`cos`/`atan2` inside the step.
- **Latest and experimental.** Prefer the newest engine features. Research current releases rather than relying on
  memory.

## Puzzle law (Ken's rule)

This is a puzzle game. The player must think. Every hole is designed so its components are **necessary**:

1. **Impossible without the tools.** With no machine placed, no swing sinks the ball. Banks, lucky bounces and
   brute force must all fail.
2. **Solvable by an idea.** With the tools placed well, a comfortable range of swings sinks it. The hard part is
   working out *where things go and why*, never pixel-perfect aim.
3. **Proven, not assumed.** `Tests/Sim/solve.sh <course>` brute-forces both claims with the real physics. A hole
   doesn't ship until it prints PASS. Re-run it after any change to the course or the physics.
4. **One swing per leg.** If the ball stops anywhere but the cup or a safe zone, it returns to the last safe spot.
   (Free multiple strokes would let players walk the ball around every obstacle.)
   **Safe zones** are optional, per level: pads where a resting ball stays, making long holes a chain of legs.
   The solver proves every leg separately.
5. **Machines bend, they don't trap.** A gravity machine pulls only while the ball approaches and releases it
   after the closest pass. (A steady pull plus rolling friction always parks the ball under the machine.)
6. **The club is a putter.** The ball rolls. Height, curves and anything else come from the machines.
7. **One new idea per hole**, taught by the level itself.

## Critique everything (Ken's rule)

Claude is the only developer, so nobody else will catch a weak decision. After every meaningful step, critique it
before moving on, and say the critique out loud in the report to Ken:

- **Decisions:** what was chosen, what the alternatives were, and what would make this choice wrong.
- **The game:** is this fun, clear and new? Would a player understand it without help? Is the puzzle an idea or
  just an aim? Compare honestly against The Talos Principle and Golf With Your Friends.
- **The look:** judge every screenshot as a harsh art director would. Name what's ugly, flat, fake or boring, and
  fix the worst thing first. "Better than before" is not the bar; the reference games are.
- **Functionality:** play it (PIE), don't assume. List what was verified in-engine and what wasn't.
- **Process:** note mistakes in how the work was done (for example, launching two editors) and fix the cause.

Never report something as good when it is merely working.

## Commands

```bash
UE="/Users/Shared/Epic Games/UE_5.9"
Tests/Sim/run.sh                                             # sim tests, no Unreal needed
python3 Tools/courses/terraces.py                            # regenerate a course JSON
Tools/rebuild.sh                                             # close editor, compile C++, restart editor with MCP
Tools/editor.sh                                              # start one editor, wait for MCP (retries if the port is held)
```

Work through the Unreal MCP (`mcp__unreal__*`) while the editor is open:

- Run repo scripts with `editor_toolset.toolsets.python_scripting.PythonScriptingTools.execute_python` and
  `runpy.run_path('<abs path>', run_name='__main__')`. Long scripts can time out on the client yet still finish;
  check the log.
- After any C++ change run `Tools/rebuild.sh` (about 2 to 3 minutes).
- Play and look: `EditorAppToolset.StartPIE` (warmupSeconds 10+), `SceneCaptureToolset.CaptureGameViewport` with
  the PIE world from `ListWorlds`, then `StopPIE`.
- Read the log with `ConsoleToolset.LogsToolset.GetLogEntries`.
- Replay a solver result in PIE with console commands (`ConsoleToolset.RunConsoleCommand`): `GGMachine x,y,z`,
  then `GGShot yaw,power`, and read `LogGGCourse` for the outcome.
- Fab installs: `FabToolset.InstallFabListing`, then save dirty packages.
- Test input without hands: `GGTouch finger,phase,x,y` (a touch, in fractions of the screen), `GGMenu
  title|pause|holes|settings|together|workshop|designs|none`, `GGWhere` (logs the player's position, facing and state).
- The Workshop from the console: `GGWorkshop tool wall`, `GGWorkshop stroke x0,y0,x1,y1` (one stroke of the tool, in
  centimetres), `test`, `build`, `undo`, `new`, `keep`, `open <name>`, `code [text]`, `check`, `json <file>`. Every call
  logs the Workshop's state.
- `execute_python` takes `{"script": {"content": "<code>"}}` and returns the last expression's value; `print`
  goes to the log only.

## Before calling a change done

```bash
Tests/Sim/run.sh && Tests/Sim/solve.sh <course>   # physics and puzzle law, after any sim or course change
Tools/smoke.sh                                    # every hole still solves in the engine
Tools/perf.sh                                     # frame rate, after any art or rendering change
Tools/testall.sh                                  # all of the above and the Workshop, co-op and host/join tests (20 min)
```

Each course records its answer with `c.solution(leg, machines, yaw, power)`; `GGDemo` (F1 in play) replays it.
Frame-rate budget: 60 fps in the editor on the M4 Max from the tee. When a hole misses it, run `ProfileGPU` in the
console and read the pass list in the log before guessing.

## Gotchas

- Run exactly one editor. Start it only with `Tools/editor.sh`, never in the background alongside another call.
  A second editor can't bind the MCP port and silently runs without it.

- A standalone `-game` launch once hung at startup compiling global shaders (just after ray tracing was enabled).
  It starts in about ten seconds now; `Tools/hosttest.sh` launches two. A `-game` copy can't bind the MCP port while
  the editor is open and logs an error about it, which is harmless.
- The first editor start after changing renderer settings recompiles shaders and rebuilds Nanite data for the
  Megaplants trees (several minutes). MCP tools return "slow task" until it finishes.
- After `ExitEditor`, the MCP port can stay held for a few seconds. If a fresh editor logs "MCP server listener
  could not start on port 8000", kill it and run `Tools/editor.sh` again.
- The editor's content-folder monitoring is turned off in config. With it on, a new `Content/Courses/*.json`
  triggers a DataTable import dialog that blocks every MCP call ("slow task") until someone clicks it.
- Playing together: the course is kept in step by commands, not replicated state. Anything that changes the hole
  must go through a `Net*` multicast on `AGGCourse` issued by the server (clients ask through `Server*` calls on
  their golfer), must give the same result on every machine, and must call `Flush()` first if it depends on the
  ball having stopped. Run `Tools/nettest.sh` after touching it.
- Automated play must not write Ken's save. `Tools/play.sh` runs `GGTestSave` as soon as play starts (an empty save
  that is never written, for that session only); standalone copies take `-GGTestSave`. Anything that starts play
  another way has to do the same.
- Stop play with `Tools/play.sh stop`, never the MCP `StopPIE` tool: it crashes the editor when a second player's
  window is open. After any editor crash, close the crash-report window (`Tools/editor.sh` does): it holds the MCP
  port and the next editor starts deaf.
- `Tools/rebuild.sh` leaves the editor closed when the build fails. Fix the error and run it again.
- The web build is made in a copy (`../gravitygolf-web`). `Tools/web.sh` copies source by content and stamps changed
  files with the time of the copy; an ordinary time-preserving copy let stale object files be linked (a source file
  edited before the last web build but copied after it looked already built). If a web build ever seems to run old
  code, `touch` everything under the copy's `Source/` and rebuild.
- Web builds: the 5.9 preview's Mac launcher build cannot target Wasm ("not supported from this engine
  distribution"; it lacks the Wasm third-party libraries, page template and tools). The editor will not even list
  the Wasm platform for cooking unless the Emscripten SDK is found (`WASM_EMSDK_ROOT=~/emsdk`, version 6.0.10).
- Weight plates (`c.switch(..., weight=True)`) are down only while a machine stands on them and are never banked
  by a pad. `GG::HoldWeightPlates` settles them before each swing; the game, the solver, the search and the probe
  all call it. The search stands a machine on a plate a third of the time.
- A dead ball inside an attractor's dome is reeled in and thrown out the far side; inside a repulsor's dome it is
  pushed straight away. Many "answers" the search finds are a ball killed on a wall and then carried by the
  machines. They pass the proof, but trace them (`Tests/Sim/probe.sh`) before recording one as the intended answer.
- One enormous box draws over things standing on it: the Workshop's table as a single 90 km slab hid a hole whose
  ground was 30 cm above it (depth precision across a huge triangle). Lay big ground in tiles of a few hundred metres.
- A material rebuilt by `Tools/build_materials.py` resets its instances. To add or change one material without
  touching the rest, run the script with `GG_ONLY` set: `runpy.run_path(path, init_globals={'GG_ONLY': ['grid']})`.
- Where two boxes share the ground under the ball, only the first one listed touches it (it seats the ball exactly
  on its surface, and the next box then sees no contact). So a safe pad's sand, listed after the floor it lies in,
  has never slowed a ball, on any hole, and must not: the next swing starts on the pad. Soft ground that should stop
  a ball goes before the floor (`c.soft_patch`), and stops it within about 20 cm. The Workshop cuts a design into
  rectangles that never overlap, sand included, so its sand works.
- Keys are not axes: `BindAxisKey(EKeys::W, ...)` trips an engine ensure at startup. Read W A S D with
  `IsInputKeyDown` in Tick.
- The forgiving move in this physics is a straight reel: ball, machine and target in one line (hundreds of working
  swings). But a straight reel from where the ball lies never needs the machine for direction: if the line is open
  a plain putt does it. A machine is necessary only where the ball must turn (fiddly: a dozen swings) or where it
  also opens the way (a weight plate on the line: hole 9). `Tests/Sim/solve.sh` now tries every pair of plinths on
  a two-machine hole with plinths; `cupscan.sh` takes `GG_LEG` and `GG_FIXED=x,y` (a second machine's spot).
- Design notes from holes that did not work. (1) A machine pinned to one spot (a weight plate) that also has to bend
  the ball is too fiddly: in open ground at most a dozen swings cross any one square slowly enough to drop, and the
  proof wants twelve that sink. Forgiving holes come from the player choosing the spot, or from walls that funnel.
  (2) Sand cannot hand a ball from one machine to the next: a ball that has stopped is not "approaching", so nothing
  pulls it, and sand's hold (882 cm/s2) is stronger than any pull (420). (3) An attractor never pulls a ball at rest.
- Adding a hole: its course and level scripts, an entry in `UGGSave::Holes()` (GGSave.cpp), the previous course's
  `next_level`, the level lists in `Tools/smoke.sh`, `Tools/perf.sh`, `Tools/regen.sh`, `Tools/web.sh` (MAPS) and
  `Tools/webtest.sh` (tour), a `hole-<Level>` fixture in `Build/Wasm/fixtures.json`, a number key in GGGolfer, and
  the table in `docs/VISION.md`. The ending card appears on whichever hole has no `next_level`.
- Test a hole's stated idea, not only the hole: change what the idea depends on (move the cup, hold the gate open)
  and check the proof changes. Hole 6's timed gate turned out to be decoration this way.
- An attractor is also a cannon: a ball tapped toward it is drawn in and released along the line through it.
  Every layout must block the straight line from the ball through any spot a machine can stand to the target, or
  the hole is trivial. The solver catches it; `Tests/Sim/search.sh` shows it as huge tolerances with one machine
  parked far away.
- Rebuilding materials (`Tools/build_materials.py`) resets every level's material instances: levels render flat
  tan until their scripts run again. `Tools/regen.sh` does this for you; never run the material script alone.
- A level script can serve several holes: `Tools/levels/returning.py` runs `canyon.py` with its own settings, and
  `stones.py` runs `saltmirror.py`.
- A sun at 50 degrees throws a 15 m wall's shadow 12 m: across a whole lane. Check the picture from the tee before
  settling a sun direction, and aim the light along long walls, not across them.
- zsh does not split an unquoted variable into words: `tool $ARGS` passes one argument. It cost two wrong scans.
- Geometry Script: the lathe (`append_revolve_polygon`) ignores the material in its options; remap it afterwards.
- Megaplants need `r.Nanite.Foliage` and `r.Nanite.AllowAssemblies`, or the trees render bare.
- Hole 1 costs about 14 ms that does not change with resolution (27 ms at full size, 20 ms at two thirds). No one
  thing owns it: clouds 2.7 ms, the 19 pines 4.3 (half of it their shadows), 164 shrubs 2.2 (their ray-tracing
  skinning), bounced light 2.9. Metal's ProfileGPU reports most passes as 0 ms, so measure by switching things off
  from Python in play (`set_cast_shadow`, `set_visible_in_ray_tracing`, `set_actor_hidden_in_game`) and `GGPerf`.
- Frame rates measured while `Tools/web.sh` is running are about 10 fps low (it has twice sent me looking for a
  regression that was not there).
- `r.ScreenPercentage` set from the console stays set for the editor session. Play defaults to about two thirds on
  this display; setting 100 "to restore it" made every later measurement 30% worse until the editor restarted.
- Megaplants are skeletal meshes that sway. Anything that sways redraws its shadow every frame: 26 pines cost 12 ms
  in Lantern Court. Turn shadows off on background plants (`skeletal_mesh_component.set_cast_shadow(False)`).
- Anything rebuilt or moved every frame (instanced markers, the club) must stay out of Lumen and ray tracing
  (`bAffectDynamicIndirectLighting`, `bAffectDistanceFieldLighting`, `bVisibleInRayTracing` all false), or Lumen
  re-captures it every frame (6 to 14 ms).
- The editor throttles to 3 fps when it is not the front app. `Config/DefaultEditorSettings.ini` turns that off;
  without it, automated play runs at 3 fps and frame-rate numbers are meaningless.
- Post-process exposure min/max brightness are luminance values, not EV; setting them high makes the game look
  like night.
- macOS 27 with Xcode 27.2 works (UE 5.9 allows up to 27.9). The Metal toolchain must be installed
  (`xcodebuild -downloadComponent MetalToolchain`).
